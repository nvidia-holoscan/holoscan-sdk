Holoscan uses independently versioned contracts for application schemas,
serialized artifacts, Channel protocols, native descriptors, and internal
compiler interfaces. A version identifies one of those contracts; it does
not count SDK releases.

This reference records the current values in the Holoscan SDK 5.0 source and
links to their definitions. It covers the nine contracts above v1 examined
during the GA versioning review, plus related contracts still at v1. Private
implementation contracts are included to help interpret artifacts and
diagnostics; their inclusion does not make them public extension interfaces.

<Note>
  Stable C++ and Python source APIs, native binary compatibility, serialized
  formats, and cross-process interoperability have separate boundaries. Use
  [API stability](/holoscan/sdk-user-guide/introduction/api-stability) for the
  source compatibility policy and the individual guides for supported
  deployment combinations.
</Note>

## Application schemas have their own identities

Application-owned schemas are separate from the SDK-owned versions listed
below:

| Family | Identity and version boundary | Where to define it |
| --- | --- | --- |
| Parameter schemas | An authored schema ID and numeric version, field identities, and derived structural/contract hashes. Nested schemas contribute their own identities. | [Parameter schemas](/holoscan/sdk-user-guide/building-operators/parameter-schemas#schema-identity-and-versioning) |
| Generated FlatBuffer payloads | Fully qualified root name, compatibility epoch, derived family ID, and four-byte file identifier. Compatible edits preserve existing field IDs and wire types. | [Custom FlatBuffer schemas](/holoscan/sdk-user-guide/data-and-payloads/custom-flatbuffer-schemas#evolve-a-schema-deliberately) |
| Raw POD payloads | Authored canonical type name and numeric version, plus the exact declared field layout. Applications coordinate producer/consumer deployment. | [Raw POD payloads](/holoscan/sdk-user-guide/advanced/experimental-pod-payloads) |

For example, an application's parameter schema version can be 1 while its
snapshot is stored in archive format v1 and its generated plan uses private
plan schema v9. Those three numbers describe different contracts. Likewise,
the schema-family derivation domain `/v2` below is independent of a
FlatBuffer family's authored compatibility epoch.

Values below describe this SDK source revision. The linked definitions and
consumers are authoritative when auditing another revision.

| Contract | Current value | Boundary and reader implications | Source definition |
| --- | --- | --- | --- |

Runtime-package matching checks whether the required plan schema is supported. | [`kPlanSchema`](https://github.com/nvidia-holoscan/holoscan-sdk/blob/main/src/compiler/plan_artifact_serialization.cpp) |
| Temporal records | `holoscan.temporal-records`, version **2** | Identifies serialized temporal-contract records. | Endpoint catalog JSON | `holoscan.channel-endpoints`, version **2** | Identifies the serialized catalog consumed by standalone clients. Parsing requires the current format and version; attaching also validates the endpoint contract. | [`kCatalogFormat` / `kCatalogVersion`](https://github.com/nvidia-holoscan/holoscan-sdk/blob/main/src/channel/endpoint_catalog.cpp) |
| Channel sample descriptor | ABI version **2** | Versions `ChannelSampleDescriptor`, a native descriptor boundary. This number is independent of the catalog JSON version and other Tensor or schema envelope ABIs. | [`kChannelSampleDescriptorAbiVersion`](https://github.com/nvidia-holoscan/holoscan-sdk/blob/main/include/holoscan/channel/types.hpp) |
| Catalog data-attribution frame | Wire version **3** | Carries data/EOS attribution and producer generation. The decoder rejects superseded v2 frames with `kProtocolError`; it has no version-negotiation fallback. | [`kDataAttributionVersion`](https://github.com/nvidia-holoscan/holoscan-sdk/blob/main/src/channel/channel_catalog_binding.cpp) |
| Catalog health-control frame | Wire version **2** | Uses the publisher's producer generation in the epoch field. | Partition planner interface | Interface version **3** | Private registration/invocation contract checked by the planner catalog. The selected partition algorithm has a separate ID and version. | [`kPartitionPlannerInterfaceVersion`](https://github.com/nvidia-holoscan/holoscan-sdk/blob/main/src/compiler/partitioning/partition_types.hpp) |
| Schema-family ID derivation | Hash domain `holoscan.schema-family/v2` | Derives a family ID from the domain, exact fully qualified root name, and compatibility epoch. A shared numeric value does not establish compatibility between these rows.
The Channel sample descriptor ABI, catalog JSON, and health-control frame are
all at version 2, but each reader checks a different contract.

## Read and upgrade artifacts deliberately

1. Identify the family first: a parameter schema, plan JSON, catalog, native
   descriptor, wire frame, or hash domain. Use that family's version field or
   identifier when selecting a reader; the enclosing SDK version alone is
   insufficient.
2. Check the reader or package's supported contract. For example,
   [runtime-package matching](https://github.com/nvidia-holoscan/holoscan-sdk/blob/main/src/runtime/runtime_package_capability.cpp)
   checks required plan schemas explicitly, and Channel frame decoders reject
   unsupported versions. A version field does not add negotiation or migration.
3. Follow the release's rebuild and matching-deployment requirements. Regenerate
   deployment artifacts with the intended SDK and review schema versions when
   comparing plan JSON or digests across SDK upgrades. Use the documented
   [plan accessors and artifact APIs](/holoscan/sdk-user-guide/advanced/plan-tooling)
   to inspect and publish them.

Source API stability alone does not establish cross-version readers, writers,
or runtime-peer interoperability. A compatible application-owned schema edit
also needs to fit its declared bounds and the supported deployment contract.
