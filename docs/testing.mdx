Because Holoscan separates *what your pipeline is* (the composed graph), *whether
it is valid* (the compiled plan), and *what your operators do* (the `compute()`
bodies), you can test each layer with ordinary tools — a C++ test framework such
as GoogleTest and your existing CI — without any Holoscan-specific harness.
Three techniques cover most of what teams need today: running a whole graph
deterministically under a simulated clock, compiling the graph in CI and
diffing the resulting plan against a baseline, and unit-testing the logic
inside `compute()` with constructed inputs.

This page shows all three, in that order. It closes with an honest note on
what is *not* here yet: a dedicated harness for running a single operator
without the full runtime is planned for a future release.

**Complete C++ examples:** [`examples/compile_and_check/cpp`](https://github.com/nvidia-holoscan/holoscan-sdk/tree/main/examples/compile_and_check/cpp)
and [`examples/time_and_clocks/cpp`](https://github.com/nvidia-holoscan/holoscan-sdk/tree/main/examples/time_and_clocks/cpp)

## Deterministic whole-graph tests with a simulated clock

The runtime never reads the OS clock directly: every trigger, temporal
selection, and timestamp goes through the graph's `Clock` abstraction. In
production the default clock tracks real time; in a test you substitute a
clock whose time *you* drive, and the same operators and wiring run unchanged
in simulated time. This is the foundation laid out in
[Time and clocks](/holoscan/sdk-user-guide/getting-started/time-and-clocks) —
here we use it for testing.

Two test clocks ship with the SDK:

- **`ManualClock`** (`<holoscan/time/manual_clock.hpp>`) — time is a plain
  value you set. Sleeps modeled through the clock move it forward immediately
  to the wake-up point instead of blocking. Best for single-threaded stepping
  and for unit tests of time math.
- **`SyntheticClock`** (`<holoscan/time/synthetic_clock.hpp>`) — sleeping
  threads genuinely *block* until another thread advances the clock past their
  target time with `advance_to()` / `advance_by()`. That releases workers in
  lock-step as synthesized time moves forward, which is what you want when a
  live graph with clock-driven triggers is running while the test drives time.

To put a graph on a test clock, bind a live clock instance you keep a handle
to, and make it the default:

```cpp
#include <gtest/gtest.h>

#include <holoscan/core/compile.hpp>
#include <holoscan/core/graph.hpp>
#include <holoscan/core/run.hpp>
#include <holoscan/time/synthetic_clock.hpp>

TEST(FusionPipeline, TenFramesOfSimulatedTime) {
  // Keep the shared_ptr: it is the handle the test uses to drive time.
  auto test_clock = std::make_shared<holoscan::SyntheticClock>(0);

  holoscan::Graph graph{"fusion-under-test"};
  auto camera = graph.op<FakeCamera>("camera");     // test double for the sensor
  auto fusion = graph.op<SensorFusion>("fusion");
  auto sink   = graph.op<RecordingSink>("sink");    // appends results for assertions
  graph.add_flow(camera->frame, fusion->frames);    // ports are declared operator members
  graph.add_flow(fusion->control, sink->in);

  const holoscan::ClockKey key = graph.bind_shared_clock("test", test_clock);
  graph.set_default_clock(key);

  const holoscan::ExecutionPlan plan = holoscan::compile(graph);
  ASSERT_TRUE(plan.ok());

  holoscan::RunSession session = holoscan::run_async(plan);

  // Drive ten camera frames of simulated time (~60 Hz).
  for (int frame = 0; frame < 10; ++frame) {
    test_clock->advance_by(std::chrono::nanoseconds{16'666'667});
  }

  session.request_stop();
  session.wait();
  EXPECT_EQ(session.termination(), holoscan::RunTermination::kStopped);
  EXPECT_EQ(recorded_controls().size(), 10u);  // state captured by RecordingSink
}
```

The pattern in words: **bind → default → compile → `run_async` → advance →
stop → assert**. Because `bind_shared_clock()` retains your live instance
(unlike `add_clock<ClockT>()`, which replays a factory into a runtime-owned
clock), the `advance_by()` calls in the test move the exact clock every
`OnClock` trigger and temporal selector in the graph reads.

Assertions belong *after* `session.wait()` returns, and results are easiest to
capture with a small test-only sink operator that appends what it receives to
state the test can inspect — the `RecordingSink` above. Operators themselves
need no changes: `compute()` reads time through `ctx.clock()` and cannot tell
a synthetic time base from a real one, which is precisely the point.

<Warning>
  **Drive time from one controlling thread.** `ManualClock`'s individual reads
  and advances are race-free, but compound operations are not serialized
  against concurrent advances — the supported pattern is a single test thread
  stepping time. `SyntheticClock` is fully synchronized, but interleaving
  multiple advancing threads still makes the *test* nondeterministic. One
  driver thread, always.
</Warning>

<Warning>
  **Advancing time is not a barrier.** `advance_by()` releases work; it does
  not wait for that work to finish. Do not assert on outputs between
  advances unless you have your own synchronization — assert after
  `session.wait()`, or have the recording sink expose a counter the test can
  poll.
</Warning>

For replaying recorded timelines and the broader determinism story (logical
order, `TagTime`, reproducible runs), see
[Determinism and replay](/holoscan/sdk-user-guide/advanced/determinism-and-replay).

## Compile-plan checks in CI

`compile()` is a pure, cold transform: it never runs `compute()`, creates
endpoints, or touches your thread's scheduling. That makes it cheap and safe
to call inside a unit test — and it turns your CI into a graph-validity gate
that catches wiring, admission, and contract errors long before hardware is
involved.

The baseline check is two lines plus diagnostics on failure:

```cpp
#include <holoscan/core/compile.hpp>
#include <holoscan/core/execution_plan.hpp>

TEST(FusionPipeline, PlanIsAdmitted) {
  holoscan::Graph graph = make_production_graph();  // your app's real composition
  const holoscan::ExecutionPlan plan = holoscan::compile(graph);

  for (const holoscan::Diagnostic& d : plan.diagnostics()) {
    // d.token is a stable registry token, not log prose — grep-able in CI logs.
    std::cerr << (d.severity == holoscan::DiagnosticSeverity::kError ? "error: " : "warning: ")
              << d.token << '\n';
  }
  ASSERT_TRUE(plan.ok());
}
```

Remember the failure model: admission failure is a **rejected plan, not an
exception**, so the test inspects `ok()` and `diagnostics()` rather than
wrapping `compile()` in a try/catch (see
[Compile and check](/holoscan/sdk-user-guide/getting-started/compile-and-check)).

The second, stronger check catches *unintended* plan changes. An admitted plan
serializes deterministically — `plan.json()` is canonical JSON and
`plan.digest()` is a 256-bit semantic digest (`holoscan::PlanDigest`, an
`std::array<std::byte, 32>` comparable with `==`) covering normalized plan
semantics. Check the digest of your known-good plan into the repository and
diff against it:

```cpp
TEST(FusionPipeline, PlanMatchesBaseline) {
  holoscan::Graph graph = make_production_graph();
  const holoscan::ExecutionPlan plan = holoscan::compile(graph);
  ASSERT_TRUE(plan.ok());

  const holoscan::PlanDigest baseline = load_baseline_digest();  // checked-in bytes
  EXPECT_EQ(plan.digest(), baseline)
      << "Execution plan changed. Review the canonical JSON diff, then refresh "
         "the baseline if the change is intentional:\n"
      << plan.json();
}
```

The division of labor: **diff with `digest()`, read with `json()`**. Digest
equality tells you *whether* the plan changed without parsing anything; when
it fails, checking the canonical JSON into the repo alongside the digest gives
reviewers a human-readable diff of *what* changed — partitioning, channel
capacities, temporal triggers, clock catalog, and the rest. A refactor that
was supposed to be behavior-neutral but silently altered an endpoint name or a
queue capacity shows up as a red CI job instead of a runtime surprise.

For plan-inspection tooling beyond assert-and-diff — record accessors,
artifact bundles, and working with plans outside tests — see
[Plan tooling](/holoscan/sdk-user-guide/advanced/plan-tooling).

<Tip>
  Compile-plan tests need no GPU and no runtime bindings, so run them in the
  cheapest CI tier on every commit. Reserve simulated-clock graph tests for
  the same tier where possible, and hardware-in-the-loop runs for merge gates.
</Tip>

## Testing `compute()` logic with constructed inputs

An operator is three declarations — `setup()` for structure, `contract()` for
time, `compute()` for work — and `compute()` is intentionally oblivious to
temporal concerns. Exploit that: keep the *work* in plain functions that take
constructed values, and let `compute()` be a thin shell that receives, calls,
and emits. The plain functions then test like any other C++ code.

```cpp
// fusion_math.hpp — pure logic, no runtime types.
Control fuse(const Frame& frame, const ImuSample& imu);

// fusion_math_test.cpp — ordinary GoogleTest, no graph, no clock, no runtime.
TEST(FuseLogic, LargeTiltCommandsCorrection) {
  const Frame frame = make_test_frame(/* ... */);
  const ImuSample imu{.tilt_rad = 0.4};
  const Control control = fuse(frame, imu);
  EXPECT_GT(control.correction, 0.0);
}
```

Inside the operator, `compute()` reduces to plumbing — receive inputs, call
`fuse()`, emit the result — so the part that carries your domain risk has
direct, fast, deterministic coverage, and the plumbing is exercised by the
simulated-clock graph tests above.

What you *cannot* do today is instantiate an operator and invoke its
`compute()` directly: the `holoscan::ExecutionContext` handed to `compute()`
is constructed by the runtime for each activation and is not something user
code can build by hand. The runtime boundary is therefore the seam — put logic
you want to unit-test on the far side of it.

<Note>
  **Planned: an operator unit-testing harness.** A dedicated harness for
  running a single operator without the full runtime — feeding its input
  ports constructed values, collecting and validating its outputs, and
  stepping activations — is planned for a future release. Until it lands, the
  factor-out-pure-logic pattern above plus simulated-clock graph tests are the
  supported approach.
</Note>

## Choosing the right layer

| You want to verify… | Use | Cost |
|---|---|---|
| Numeric/domain logic is correct | Pure-function unit tests with constructed inputs | Milliseconds, no runtime |
| The graph is valid and unchanged | Compile in a test: `ok()` + digest/JSON baseline | Milliseconds, no runtime |
| Operators interact correctly over time | Whole-graph run under `SyntheticClock` | Seconds, full runtime, no hardware |
| Real sensors and drivers behave | Hardware-in-the-loop run | Minutes, real devices |

Work down the table only as far as the property under test requires; each row
down costs more and diagnoses less precisely. When a graph-level test fails,
the failure taxonomy in
[Understanding failures](/holoscan/sdk-user-guide/debugging-and-testing/understanding-failures)
tells you which phase — authoring, compile, or run — to look at first.

## Recap

- The whole runtime reads one swappable `Clock`: bind a `SyntheticClock` with
  `bind_shared_clock()` + `set_default_clock()` and drive `advance_by()` from
  a single test thread for deterministic whole-graph tests.
- `ManualClock` steps time as a plain value; `SyntheticClock` blocks sleepers
  until time is advanced — use the latter for live graph runs.
- Compile the graph in CI: assert `plan.ok()`, log `Diagnostic` tokens on
  failure, and diff `plan.digest()` / `plan.json()` against a checked-in
  baseline to catch unintended plan changes.
- Keep `compute()` a thin shell over pure functions and unit-test those with
  constructed inputs; user code cannot build an `ExecutionContext` by hand.
- A dedicated operator unit-testing harness (running operators without the
  full runtime) is planned for a future release.
