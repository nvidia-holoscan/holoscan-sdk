Most of an operator's life is spent in `compute()` — the steady-state,
per-activation work. But some work belongs *around* steady state, not inside
it: validating immutable configuration, reserving a finite pool, warming up a
model, and later releasing everything cleanly. Lifecycle callbacks are where
that setup and teardown work lives, and the runtime drives them through a small
set of global stage barriers so the work is ordered correctly across every
operator in the graph.

This page shows the two ways to author that work — the simple
`start()`/`stop()` overrides and the advanced sparse stage callbacks — when
each hook actually runs, what an advanced callback can do through its
`LifecycleContext`, how to order lifecycle work across operators, what happens
when lifecycle work fails, and how restarts are authorized and requested.

**Complete C++ example:** [`examples/lifecycle_callbacks/cpp`](https://github.com/nvidia-holoscan/holoscan-sdk/tree/main/examples/lifecycle_callbacks/cpp)

  **Beta.** Everything on this page works today as described: both authoring
  paths, the stage barriers, cross-operator ordering, phase-selected parameter
  views, and the rollback semantics. The API may still evolve in upcoming

## The eight stage barriers

The runtime models startup and shutdown as eight **global stage barriers**.
Every operator's callback for a stage completes before any operator advances to
the next stage. When a forward stage fails, the work completed in that pass is
rolled back in **reverse completion order**. Ordinary shutdown is not a blanket
reverse replay: it runs the compiled `kStop` and `kRelease` plans, in which
authored teardown dependencies take precedence and only independent same-level
`kStop` peers unwind in reverse of their successful start order.

Six forward (startup) stages run in this order:

| Stage | Intent |
|---|---|
| `kConfigure` | Validate immutable configuration and derive cold intent. |
| `kDiscover` | Discover external capabilities without publishing readiness. |
| `kAllocate` | Reserve admitted finite runtime resources (pools, devices). |
| `kWarmUp` | Prepare resources without making the operator activatable yet. |
| `kArm` | Bind current-generation external and readiness capabilities. |
| `kStart` | Publish the operator as ready for steady-state activation. |

Two teardown stages run on shutdown; the same pair also unwinds completed
forward work when a startup pass or a restart's forward suffix fails:

| Stage | Intent |
|---|---|
| `kStop` | Close activation acceptance and quiesce steady-state work. |
| `kRelease` | Release resources owned by the active lifecycle epoch. |

The helper `is_lifecycle_forward_stage()` returns `true` only for `kConfigure`
through `kStart`; the teardown stages are never valid restart entry points
(more on restarts below). An authorized restart re-enters the forward chain at
a chosen forward stage — such as `kAllocate` — as a single transaction.

## Two authoring paths, one checkpoint model

Every operator has one logical checkpoint slot per stage, and two authoring
paths can fill those slots. They meet in the *same* slots, which is what keeps
the rules below simple.

### The simple path: override `start()` and `stop()`

For plain setup and teardown at the start/stop boundary, override the public
virtuals `Operator::start()` and `Operator::stop()`:

```cpp
class Recorder final : public holoscan::Operator<RecorderParams> {
 public:
  void start() override {          // runs as the kStart checkpoint
    writer_.open(params().path);   // params() is phase-selected here
  }
  void stop() override {           // runs as the kStop checkpoint
    writer_.close();
  }
  // setup(), contract(), compute() as usual ...

 private:
  Writer writer_;
};
```

Graph authoring detects the overrides when the operator is added with
`graph.op<T>(...)` and lowers each one as a **required** callback in the same
checkpoint slot the advanced path uses: `start()` runs as your `kStart`
checkpoint, `stop()` as your `kStop` checkpoint. Your 4.x overrides port
unchanged (see
[migrating from 4.x](/holoscan/sdk-user-guide/introduction/migrating-from-4x)),
the no-argument `void` signatures remain valid, and nothing about the advanced
path deprecates them.

Inside `start()`/`stop()` the operator reads its parameters through
`Operator::params()`, which the runtime points at the exact phase-selected
generation before invoking the hook. Because `stop()` returns `void` and takes
no context, it cannot report a cleanup failure as a value (a thrown exception
is converted to `kFatalFailure`), and it cannot observe the cancellation
latch.

### The advanced path: sparse stage callbacks

When work belongs at another stage (`kAllocate`, `kArm`, …), when you need
`LifecycleContext` services, or when `stop()`'s `void` return cannot express a
cleanup failure, register sparse callbacks per stage, inside `setup()`,
through the fluent `spec.lifecycle()` builder. An operator with no lifecycle
work registers nothing, and the runtime records a successful skipped
checkpoint for it at every barrier.

Each advanced callback is a member function with the exact signature
`LifecycleStatus method(LifecycleContext&) noexcept`. The builder takes a typed
member pointer, so the operator type is deduced — no string names:

```cpp
void setup(holoscan::OperatorSpec& spec) override {
  spec.input(frames_);
  spec.lifecycle()
      .stage(holoscan::LifecycleStage::kAllocate, &Detector::allocate)    // required
      .optional(holoscan::LifecycleStage::kWarmUp, &Detector::warm_up);   // may be absent
}

holoscan::LifecycleStatus allocate(holoscan::LifecycleContext& ctx) noexcept {
  // ... reserve a finite pool ...
  return holoscan::LifecycleStatus::kOk;
}
```

`.stage(...)` registers a required callback; `.optional(...)` registers one
whose *absence* would have been permitted. If you need ordering within a
stage, express it across operators (see below) rather than stacking callbacks.

Registration itself is a cold authoring call: it can throw `std::bad_alloc`,
and an invalid stage, a duplicate stage, or a member pointer that does not
belong to the exact concrete operator type is reported when graph authoring
validates the declaration — not at the `.stage(...)` call itself.

### At most one application callback per stage

The two paths meet at the same checkpoint slots, so **at most one application
callback** may fill a slot. An operator that overrides `start()` cannot also
register an advanced `kStart` callback (and likewise for `stop()`/`kStop`);
graph authoring rejects the conflict with `GRAPH_LIFECYCLE_CALLBACK_DUPLICATE`
when the operator is added. Mixing *across* stages is fine — advanced `kStart`
plus a plain `stop()` override is valid. At run time, Core invokes the one
callback that fills a slot, or records a successful skipped logical checkpoint
when neither path fills it. It never invokes an advanced callback and then the
virtual for the same stage.

| You author | What runs |
|---|---|
| `start()` override only | The override, as the required `kStart` checkpoint |
| Advanced `kStart` only | The advanced callback |
| `stop()` override only | The override, as the required `kStop` checkpoint |
| Advanced `kStop` only | The advanced callback |
| `start()` override **and** advanced `kStart` | Rejected at graph authoring: `GRAPH_LIFECYCLE_CALLBACK_DUPLICATE` |
| `stop()` override **and** advanced `kStop` | Rejected the same way |
| Advanced `kStart` plus `stop()` override (or the mirror) | Valid — the callbacks occupy different stage slots |
| Two advanced callbacks for one stage | Rejected when graph authoring replays `setup()` |
| Nothing for a stage | A successful skipped checkpoint that still satisfies ordering |

## When lifecycle stage callbacks actually run

Lifecycle stage callbacks — from `kConfigure` through `kRelease`, including
simple `start()`/`stop()` hooks lowered into `kStart`/`kStop` — run only during
`RunSession` lifecycle transitions. Operator construction, declaration, and
contract validation happen earlier and may be replayed:

- **Graph authoring constructs a prototype.** `graph.op<T>()` constructs the
  authoring operator and calls its `setup()` declaration method.
- **Compile replays declarations and contracts.** `compile()` constructs
  temporary factory instances and calls `setup()` and `contract()` while
  validating and lowering the plan. An accepted parameter override can add
  another constructor/`setup()` replay for each affected operator. No
  lifecycle stage callback executes before `run()`/`run_async()`.
- **Each run constructs fresh operators.** A `RunSession` rebuilds every
  runtime operator from its factory, calls `setup()`, and validates the replayed
  `contract()` before any lifecycle stage callback. Treat constructors,
  `setup()`, and `contract()` as deterministic, repeatable declaration and
  validation code: do not acquire external resources or perform externally
  visible work there. Acquire external resources in lifecycle callbacks instead.
  `start()` is not a constructor substitute, and ordinary operator-instance
  state from one run is not retained by the next.
- **Startup is stage-major.** The six forward stages run one at a time behind
  global barriers: every operator finishes stage N before any operator enters
  stage N+1. Only after every operator's `kStart` completes does the runtime
  arm notifications, bind readiness sources, open control ingress, and enter
  the compute dispatch loop — in the initial startup of a run, the first
  `compute()` always happens after the last `kStart`.
- **Callbacks run on the operator's execution lane.** Each callback body is
  dispatched synchronously onto its operator's assigned lane — not on the
  thread that called `run()`/`run_async()` — serially and in deterministic
  order: topological levels, then a stable registration-keyed order within a
  level. EA1 never runs two callbacks of one transition in parallel.
- **Shutdown fences inputs first.** On drain, `request_stop()`, or failure,
  the runtime first cancels readiness sources, closes notifications, stops
  channels, and closes tensor resources; only then does the `kStop` stage run,
  followed by `kRelease`, and finally the lanes stop. Advanced teardown
  callbacks can observe `ctx.cancellation().stop_requested() == true` when a
  stop has been requested; a simple `stop()` has no context parameter and
  cannot read the latch.
- **Restarts re-run hooks mid-run.** A published restart tears down through
  `kStop` (plus `kRelease` for early re-entry stages) and re-runs the forward
  suffix, so `start()`/`stop()` and advanced callbacks can run several times
  in one run. Restart teardown is *not* a cancellation request — the latch
  stays unset unless the run is actually stopping. See
  [restart control](/holoscan/sdk-user-guide/advanced/restart-control).

## Callback results: `LifecycleStatus`, not exceptions

Advanced lifecycle callbacks are `noexcept` and report their disposition as a
value, consistent with the SDK-wide errors-as-values model. (Simple
`start()`/`stop()` overrides return `void`; their failure story is in the next
section.) The four statuses:

| Status | Meaning |
|---|---|
| `kOk` | The stage completed successfully. |
| `kSkipped` | The stage completed successfully without application work — distinct from `kOk`. |
| `kRetryableFailure` | The stage failed for a cause classified as retryable. |
| `kFatalFailure` | The stage failed and the run cannot continue. |

<Warning>
  Two sharp edges. First, each eligible callback is attempted **once per
  transition pass**, with no automatic retry or backoff: `kRetryableFailure`
  is a *classification* for future retry policy and is treated today like any
  other failure of the pass. (A later admitted restart is a new transaction —
  it can perform pre-restart teardown, a candidate forward attempt, rollback,
  and old-state restoration, and your callback runs once in each phase it is
  eligible for.) Second, a callback registered with `.optional(...)` that is
  present and returns a failure **still fails** the transition — optional
  means *absence* is permitted, not that failures are ignored.
</Warning>

## When lifecycle work fails

The two paths fail differently, but both fail closed:

- **Advanced callbacks cannot throw.** They are `noexcept` by signature — an
  exception that reaches the boundary terminates the process. Report failure
  as a `LifecycleStatus` value instead.
- **Simple `start()`/`stop()` may throw.** The runtime catches the exception
  and converts it to `kFatalFailure`; nothing escapes `run()`.

A failed **startup** rolls the run back and fails it:

- Work completed in the startup pass unwinds in reverse completion order —
  `kStop` runs for operators that completed `kArm` or `kStart`, then
  `kRelease` for operators that completed `kAllocate`.
- Simple `stop()` follows a **positional prefix rule** during startup
  rollback: it runs only for operators that successfully completed `kStart`
  before the failing position in flattened start order. The failing operator's
  own `stop()` is skipped — even when its `start()` body was entered before
  throwing — and so is everything at or after its position. Advanced `kStop`
  callbacks are not subject to that cutoff; they keep ordinary rollback
  eligibility after a completed `kArm`.
- The run reports `RunTermination::kFailed` with the diagnostic token
  `RUNTIME_LIFECYCLE_CALLBACK_FAILED`, and the later shutdown pass is a no-op
  — `stop()` is never invoked twice for one failure.

A failed **`kStop` during ordinary shutdown never aborts cleanup**: the
runtime keeps invoking every other eligible `kStop`, still runs `kRelease`,
and only then marks the run failed with the same token. See
[understanding failures](/holoscan/sdk-user-guide/debugging-and-testing/understanding-failures)
for how the token surfaces in `diagnostics()`.

## Inside a callback: `LifecycleContext`

A callback receives a `LifecycleContext&` — a borrowed, callback-lifetime
facade. It exposes exactly the cold services a stage needs, and deliberately
nothing that could submit or await lifecycle work itself:

- `ctx.cancellation().stop_requested()` — a cooperative stop /
  fatal-shutdown latch. In a **forward** callback, check it before beginning
  new work and return `kSkipped` only when no work was created. In `kStop` or
  `kRelease`, cancellation never removes the callback's teardown obligations:
  perform every required quiescence and release action, using the latch only
  to omit optional work or shorten optional waits.
- `ctx.params<Params>()` — the complete immutable parameter aggregate selected
  for **this** callback phase. Repeated calls return the same address, and the
  `Params` type must match the operator's declared aggregate exactly.
- `ctx.params_generation()` — the phase-selected parameter generation number.
- `ctx.transition_phase()` — which transition phase selected this callback's
  state view (startup, pre-restart teardown, restart forward, rollback,
  restore, or shutdown).
- `ctx.resolve_clock(key)` → `expected<ClockRef, Error>` — resolve a declared
  clock for this generation. Resolution is cold-only; no compute-time lookup is
  installed.
- `ctx.restart_target(ref)` → `expected<OperatorRef, Error>` — bind an
  already-authorized plan target to the current run generation. This resolves
  *identity* only; it does not submit a restart.

```cpp
holoscan::LifecycleStatus allocate(holoscan::LifecycleContext& ctx) noexcept {
  if (ctx.cancellation().stop_requested()) {
    // Forward kAllocate: no work started, so nothing needs unwinding.
    return holoscan::LifecycleStatus::kSkipped;
  }
  const DetectorParams& p = ctx.params<DetectorParams>();   // phase-selected params
  // ... reserve a pool sized from p ...
  return holoscan::LifecycleStatus::kOk;
}
```

<Warning>
  **`params<T>()` in a callback is phase-selected.** During a restart, the
  parameter view a callback sees may be the *candidate* generation or the old
  one — not necessarily the generation `compute()` reads. Read parameters fresh
  inside each callback rather than caching a reference across stages. Simple
  `start()`/`stop()` overrides read the same phase-selected view through
  `Operator::params()`. See
  [typed parameters](/holoscan/sdk-user-guide/getting-started/typed-parameters)
  for the parameter model itself.
</Warning>

## Ordering across operators

The stage barriers already order work *between* stages. Within a stage, two
declarative mechanisms order work across operators; the runtime lowers both
into a deterministic dependency graph, so nothing depends on construction
order.

**Same-stage facts, declared per operator.** An operator declares that its
checkpoint at a stage `produces` a named fact; another declares a
`requires_dependency` on that fact at a stage. The producer's checkpoint then
completes before the requirer's:

```cpp
inline constexpr holoscan::LifecycleDependencyKey kPoolReady{"detector.pool.ready"};
inline constexpr holoscan::LifecycleDependencyKey kUpstreamArmed{"sensor.armed"};

spec.lifecycle()
    .stage(holoscan::LifecycleStage::kAllocate, &Detector::allocate)
    .produces(holoscan::LifecycleStage::kAllocate, kPoolReady)             // I satisfy this fact...
    .requires_dependency(holoscan::LifecycleStage::kArm, kUpstreamArmed);  // ...and I need this one
```

**Direct order, declared at graph scope.** From the containing graph, order two
operators' checkpoints in the same stage directly:

```cpp
graph.lifecycle()
    .before(producer, consumer, holoscan::LifecycleStage::kStart);  // producer's kStart first
```

Prefer dependency facts when the operator itself knows what it provides or
needs (they travel with the operator and stay valid in any graph); use
`before(...)` when the ordering is a property of one particular composition.

## Restart: graph permissions, operator and external requests

Restart authority is **deny-by-default**: nothing can restart an operator
unless the containing graph granted a matching permission at authoring time.

```cpp
graph.lifecycle()
    .allow_self_restart(worker)                    // worker may request its own restart
    .allow_external_restart(worker)                // external run control may restart worker
    .allow_restart_request(supervisor, worker);    // supervisor may request worker's restart
```

An **operator-originated** restart is requested at run time from `compute()`,
through the `ExecutionContext`. External control code running outside Runtime
callbacks — such as an application supervisor — instead uses a restricted
`LifecycleControlHandle`, described on the
[restart control](/holoscan/sdk-user-guide/advanced/restart-control) page.
Handle submission from a Runtime callback is rejected, and a
`LifecycleContext` deliberately cannot submit through either path. These rules
keep callbacks from re-entering the lifecycle machinery that is running them:

```cpp
holoscan::expected<void, holoscan::Error> compute(holoscan::ExecutionContext& ctx) override {
  // Restart myself from a forward stage (requires allow_self_restart):
  HOLOSCAN_TRY(auto receipt,
               ctx.request_restart(holoscan::LifecycleRestartOptions{
                   .from_stage = holoscan::LifecycleStage::kAllocate}));
  (void)receipt;  // LifecycleRestartReceipt: run-scoped identity of the accepted request
  return {};
}
```

A two-argument `ctx.request_restart(target, options)` overload requests the
restart of an authorized *other* operator. The `from_stage` must be a forward
stage (`kConfigure` through `kStart`) — `kStop` and `kRelease` are
teardown-only and can never be a restart entry point. The `reason` field in
`LifecycleRestartOptions` is a registered audit code, not free text.

Restart semantics — coalescing, rollback, transaction states, and external run
control — have their own page: see
[restart control](/holoscan/sdk-user-guide/advanced/restart-control).

## Putting it together

A `Detector` that reserves a pool at `kAllocate`, optionally warms up at
`kWarmUp`, and orders itself against an upstream operator's readiness:

```cpp
struct DetectorParams { std::uint32_t pool_size{8}; };
// Declare its schema with HOLOSCAN_PARAM_SCHEMA as usual (see the
// parameter-schemas page, linked below).

inline constexpr holoscan::LifecycleDependencyKey kPoolReady{"detector.pool.ready"};
inline constexpr holoscan::LifecycleDependencyKey kUpstreamArmed{"sensor.armed"};

class Detector final : public holoscan::Operator<DetectorParams> {
 public:
  holoscan::Input<Frame> frames_{"frames"};

  void setup(holoscan::OperatorSpec& spec) override {
    spec.input(frames_);
    spec.lifecycle()
        .stage(holoscan::LifecycleStage::kAllocate, &Detector::allocate)      // required
        .optional(holoscan::LifecycleStage::kWarmUp, &Detector::warm_up)      // absence OK
        .produces(holoscan::LifecycleStage::kAllocate, kPoolReady)            // I satisfy this...
        .requires_dependency(holoscan::LifecycleStage::kArm, kUpstreamArmed); // ...and need this
  }

  holoscan::expected<void, holoscan::Error> compute(holoscan::ExecutionContext&) override {
    return {};  // steady-state work goes here
  }

  holoscan::LifecycleStatus allocate(holoscan::LifecycleContext& ctx) noexcept {
    if (ctx.cancellation().stop_requested()) {
      // Forward kAllocate: no work started, so nothing needs unwinding.
      return holoscan::LifecycleStatus::kSkipped;
    }
    const DetectorParams& p = ctx.params<DetectorParams>();  // phase-selected
    pool_.reserve(p.pool_size);                              // reserve finite resources
    return holoscan::LifecycleStatus::kOk;
  }

  holoscan::LifecycleStatus warm_up(holoscan::LifecycleContext&) noexcept {
    return pool_.empty() ? holoscan::LifecycleStatus::kSkipped  // nothing to warm
                         : holoscan::LifecycleStatus::kOk;
  }

 private:
  Pool pool_;
};
```

This listing is an illustrative variant. The shipping
`lifecycle_callbacks` example demonstrates the same sparse stage registration,
dependency ordering, optional `kStart`/`kStop` callbacks, and recorded
startup/teardown evidence.

For how `DetectorParams` declares its schema, see
[parameter schemas](/holoscan/sdk-user-guide/building-operators/parameter-schemas).

## Recap

- Startup and shutdown run through eight global stage barriers: `kConfigure` →
  `kDiscover` → `kAllocate` → `kWarmUp` → `kArm` → `kStart`, with `kStop` and
  `kRelease` for teardown.
- Two authoring paths fill the same checkpoint slots: override
  `start()`/`stop()` for the simple path, or register sparse advanced
  callbacks with `spec.lifecycle().stage(...)`/`.optional(...)`. Every operator
  has one logical checkpoint per stage, and at most one application callback
  may occupy it. A same-stage conflict is rejected with
  `GRAPH_LIFECYCLE_CALLBACK_DUPLICATE`; an empty slot is a successful skipped
  checkpoint; and cross-stage mixing is valid. Most operators register nothing
  or just `kAllocate`/`kRelease`.
- Lifecycle stage callbacks run only in `RunSession` transitions. Authoring
  constructs a prototype and calls `setup()`; compile and each `RunSession`
  reconstruct operators and replay `setup()` plus `contract()` validation
  before lifecycle startup. Every `kStart` precedes the first `compute()`,
  inputs are fenced before `kStop`, and `stop()`/`start()` may repeat under
  restarts.
- Advanced callbacks are `noexcept` and return `LifecycleStatus`; `kSkipped`
  is a distinct success; one attempt per eligible callback per transition
  pass, with no automatic retry; and a present optional callback that fails
  still fails the transition. A throwing `start()`/`stop()` becomes
  `kFatalFailure`.
- Startup rollback unwinds in reverse completion order and applies the
  completed-`kStart` prefix rule to simple `stop()`; a `kStop` failure during
  ordinary shutdown never aborts cleanup.
- `LifecycleContext` provides cancellation, phase-selected `params<T>()`,
  clock resolution, and restart-target identity binding — read parameters fresh
  in every callback (simple hooks read `Operator::params()` instead).
- Order within a stage with `produces`/`requires_dependency` facts or
  `graph.lifecycle().before(...)`, never by construction order.
- Restart permission is deny-by-default at graph scope. Operators request from
  `compute()` via `ExecutionContext::request_restart(...)`; external
  supervisors use a restricted `LifecycleControlHandle`. Lifecycle callbacks
  cannot submit through either path.
