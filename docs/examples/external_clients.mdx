Every example so far has lived inside a single graph: operators wired with
`add_flow()`, compiled into one plan, run by one process. This walkthrough
crosses the process boundary. The `ea1_external_clients` example ships two
small standalone programs — a **sensor daemon** that publishes IMU samples
into a running graph, and a **recorder** that consumes the graph's exported
control result — and neither of them is an operator, contains a graph, or
links against anything beyond `holoscan::core`.

The runnable source lives at `public/examples/ea1_external_clients/` in the
SDK tree.

What makes this work is a deliberately narrow contract: the graph process
serializes its **endpoint catalog** to a JSON file, and each external client
loads that file and attaches to one named endpoint through the
`ChannelRuntime` client API. Nothing else is shared — no compiled plan, no
in-memory objects, no transport handles. Because cross-process attachment is
asynchronous, both clients wrap their I/O in small, principled retry loops,
and those loops are the real lesson of this page.

<Warning>
  **Developer preview.** Interprocess channels and the standalone client API
  are a developer preview: cross-process payloads carry bounds (for example,
  cross-process tensors — host-pageable, pinned-host, or CUDA-device backed —
  are always read-only on import), and the API surface may evolve in upcoming
  releases. Verify against the headers in your installed SDK before relying
  on details.
</Warning>

## Two processes, one artifact

When you `compile()` a graph that declares `import_topic` / `export_topic`
boundaries, the resulting plan carries an **endpoint catalog**: a description
of every boundary endpoint — its name, payload identity, and queue policy.
The graph process saves that catalog to disk and passes the path to its
peers (via `argv`, an environment variable, or however you launch them):

```cpp
// In the graph process, after compile():
auto saved = plan.endpoint_catalog().save_json("/tmp/catalog.json");
if (!saved) { /* branch on saved.error().code */ }
```

The catalog file is the *entire* contract. Either side may start first, a
peer built from a different binary can attach as long as it loads the same
catalog, and a wrong or stale catalog fails at attach time — with a typed
error, not a hang. When the boundary changes, regenerate and re-share the
file.

Each endpoint in the catalog has a deployment-stable name, which the graph
side assigns when declaring the topic:

```cpp
holoscan::TopicOptions options;
options.endpoint_name = "ea1.camera_imu.imu";  // the name external clients attach by
auto imported = graph.import_topic<std::uint32_t>(
    "holomq://ea1.camera_imu.imu", options);
```

<Warning>
  **One graph, one vocabulary.** Inside a graph, operators communicate through
  typed ports (`Input<T>`/`Output<T>`) wired with `add_flow()` — the runtime
  materializes the channels for you. The `ChannelRuntime` client API exists
  only for standalone processes outside any graph. Never mix the two: using
  `ChannelRuntime` inside an operator bypasses the compiled plan and its
  guarantees.
</Warning>

## Attaching: catalog in, endpoint out

Both clients open identically. Load the catalog, create a `ChannelRuntime`,
and attach to the named endpoint — every step returns
`holoscan::expected`, so a standalone client gets the same errors-as-values
discipline as an operator. From `ea1_sensor_daemon`:

```cpp
auto catalog = holoscan::ChannelEndpointCatalog::load_json(argv[1]);
if (!catalog) {
  std::cerr << "catalog load failed: "
            << holoscan::error_code_name(catalog.error().code) << '\n';
  return 4;
}
auto runtime = holoscan::ChannelRuntime::create();
if (!runtime) { /* ... */ }
auto publisher = runtime->create_publisher<std::uint32_t>(*catalog, argv[2]);
if (!publisher) { /* ... */ }
```

The recorder differs by one line — `create_subscriber<std::uint32_t>`
instead of `create_publisher`. Note what is *absent*: no transport
configuration, no broker address, no serialization setup. The catalog
already pins all of that; the client only names which endpoint it wants.

`create_publisher` succeeding does **not** mean a peer is connected.
Cross-process attachment completes asynchronously, in the background, which
is why everything that follows is a loop.

## The sensor daemon: retry what is provably safe

The daemon publishes a finite stream of `uint32_t` IMU samples, each stamped
with a caller-owned capture timestamp. Before publishing, it waits (with a
deadline) for at least one subscriber to appear, polling
`update_connections()` to refresh the connection snapshot and
`has_subscribers()` to check it:

```cpp
const auto deadline = std::chrono::steady_clock::now() + 5s;
while (std::chrono::steady_clock::now() < deadline) {
  auto updated = publisher.update_connections();
  if (!updated) { return holoscan::make_unexpected(std::move(updated).error()); }
  if (publisher.has_subscribers()) { return {}; }
  std::this_thread::sleep_for(5ms);
}
return holoscan::make_unexpected(holoscan::Error{holoscan::ErrorCode::kTimeout});
```

The publish loop is where the example earns its keep. `emit_captured(value,
capture_timestamp_ns)` returns a positive recipient count on success. The
daemon treats that success as delivery. Everything else follows one rule —
**retry only outcomes that provably did not publish**:

```cpp
auto emitted = publisher.emit_captured(value, capture_timestamp_ns);
if (emitted) { return emitted; }  // delivered
if (!emitted &&
    emitted.error().code != holoscan::ErrorCode::kNotReady &&
    emitted.error().code != holoscan::ErrorCode::kBackpressured) {
  return holoscan::make_unexpected(std::move(emitted).error());  // terminal
}
// Pre-submit kNotReady/kBackpressured: not published — retry.
std::this_thread::sleep_for(5ms);
```

<Warning>
  **Never retry an indeterminate publication.** The pre-submit `kNotReady` and
  `kBackpressured` errors prove that the sample was not delivered. Leave the
  retry loop on any other error and handle it according to that error's
  contract. In particular, `kPublicationPartial` and
  `kPublicationIndeterminate` consume publication authority and are terminal
  for that sample because retrying may duplicate a delivery.
</Warning>

The daemon also calls `update_connections()` at the top of every retry
iteration and propagates any refresh failure instead of looping blindly — a
dead transport should end the loop, not spin it until the deadline.

## Ordered end-of-stream

A finite stream is not finished when the last sample goes out; it is
finished when downstream has observed end-of-stream. The daemon ends with a
`close()` loop shaped like the publish loop:

```cpp
auto closed = publisher.close();
if (closed) { return {}; }
if (closed.error().code != holoscan::ErrorCode::kNotReady) {
  return holoscan::make_unexpected(std::move(closed).error());
}
// kNotReady proves no receiver observed EOS yet and leaves the
// publisher usable; anything else consumes the facade and is terminal.
```

The same retry rule applies: `kNotReady` proves the close did not take
effect and the publisher is still usable, so retrying is safe. Any other
close failure consumes the publisher and is terminal. Only after the close
succeeds does the daemon report completion — samples published, total
recipient deliveries, and the catalog digest (`catalog->digest()`, a
normalized fingerprint that both sides can log to confirm they loaded the
same contract).

## The recorder: poll until connected

The consuming side is simpler because the poll loop does double duty:
`receive_sample()` returns `kNotReady` both while the transport is still
connecting *and* while no sample is pending, so one deadline-bounded loop
handles attach and receive together. From `ea1_result_recorder`:

```cpp
const auto deadline = std::chrono::steady_clock::now() + 10s;
while (std::chrono::steady_clock::now() < deadline) {
  auto sample = subscriber.receive_sample();
  if (sample || sample.error().code != holoscan::ErrorCode::kNotReady) {
    return sample;  // got one, or hit a real error
  }
  std::this_thread::sleep_for(2ms);
}
```

A received sample carries its payload in `sample->data` and public
`SampleMetadata` in `sample->metadata` — the publication `sequence`, the
producer's `capture_timestamp_ns`, and the `source_clock_id` naming the
clock domain that timestamp belongs to. The recorder prints these alongside
the catalog digest:

```cpp
const holoscan::SampleMetadata& metadata = sample->metadata;
std::cout << "value=" << sample->data
          << " sequence=" << metadata.sequence
          << " capture_timestamp_ns=" << metadata.capture_timestamp_ns
          << " source_clock_id=" << metadata.source_clock_id.value << '\n';
```

Metadata is the *public* record only: transport-level lifecycle evidence
(such as producer-epoch history) lives in runtime traces, not in
`SampleMetadata`.

## Running the pair

Both programs take the catalog path and the endpoint name on the command
line; the daemon additionally accepts a sample count, period, and first
value:

```bash
ea1_sensor_daemon <catalog.json> <endpoint> [count] [period-ms] [first-value]
ea1_result_recorder <catalog.json> <endpoint>
```

These commands require a separately running deployed graph that owns the
catalog endpoints. `ea1_camera_imu_control --emit-artifacts` only writes the
deployment bundle; it does not start that graph or its Channel services. EA1
does not ship an author-facing graph-only launcher for this manual
three-process recipe, so use the no-argument camera/IMU reference executable
for an end-to-end smoke test. Once the deployed graph is running, launch either
client in any order — the retry loops absorb the startup race. These
intentionally small acceptance companions are independently tested
attach-and-retry templates, not a general device-adapter or recording product.

## Recap

- The serialized endpoint catalog is the **only** thing the graph process
  and an external client share: `save_json` on one side, `load_json` on the
  other, attach by deployment-stable endpoint name.
- Graphs use ports and `add_flow()`; standalone processes use
  `ChannelRuntime` with `create_publisher` / `create_subscriber`. Never mix
  the two vocabularies.
- Attach is asynchronous: wrap `emit_captured`, `receive_sample`, and
  `close` in deadline-bounded retry loops, refreshing with
  `update_connections()` on the publish side.
- Retry only provably-unpublished outcomes — pre-submit `kNotReady` or
  `kBackpressured`. Partial and indeterminate publications are terminal. For
  `close()`, retry only `kNotReady`; every other close failure is terminal.
  Leave other emit errors for code-specific handling.
- A finite stream completes only after an ordered end-of-stream `close()`
  succeeds; log the catalog digest on both sides to confirm a shared
  contract.
