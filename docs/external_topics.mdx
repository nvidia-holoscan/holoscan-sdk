Most of a Holoscan application lives inside one graph: operators exchange data
through typed ports, and `add_flow()` wires them together. But real systems
rarely end at the graph boundary. A sensor daemon in another process feeds you
samples; a control loop elsewhere on the machine consumes your output. This
page shows how a graph declares those boundaries — **external topics** — and
how the compiled plan turns them into a precise, inspectable contract that
external processes can attach to.

The key idea is separation of concerns across the compose → compile → run
phases. During **compose**, you declare a boundary with `import_topic<T>()` or
`export_topic<T>()`, exactly as cold and typed as any other authoring call.
During **compile**, the plan records every boundary in an **endpoint catalog**.
During **run**, the graph side binds automatically — you never write transport
code inside the graph. Everything an external process needs to know lives in
the catalog, and nothing else crosses the boundary.

[`examples/ea1_external_clients/sensor_daemon/cpp`](https://github.com/nvidia-holoscan/holoscan-sdk/tree/main/examples/ea1_external_clients/sensor_daemon/cpp),

## Declaring a boundary

An external topic is declared on the `Graph` during composition, alongside your
operators and flows. `import_topic<T>()` brings data **into** the graph from an
external producer; `export_topic<T>()` sends data **out** to an external
consumer. Both take an exact, nonempty `holomq://` URI that identifies the
topic, plus an optional `TopicOptions` value:

```cpp
holoscan::Graph g{"sensor-pipeline"};

holoscan::TopicOptions imu_options;
imu_options.endpoint_name = "imu";
const auto imu = g.import_topic<std::uint32_t>("holomq://imu", imu_options);

holoscan::TopicOptions control_options;
control_options.endpoint_name = "control";
const auto control = g.export_topic<std::uint32_t>("holomq://control", control_options);
```

The returned handles are typed: `import_topic<T>` returns an
`ImportedTopic<T>`, and `export_topic<T>` returns an `ExportedTopic<T>`. Each
exposes exactly one graph-side port that you wire like any operator port:

- `ImportedTopic<T>::output()` — the graph-side `Output<T>` that feeds your
  operators. External data *enters* here, so from inside the graph it looks
  like a source output.
- `ExportedTopic<T>::input()` — the graph-side `Input<T>` that your operators
  feed. Data *leaves* here, so from inside the graph it looks like a sink
  input.

Wiring uses ordinary `add_flow()`, with the same type checking as any other
edge:

```cpp
auto fusion = g.op<WindowFusion>("fusion");

add_flow(imu.output(), fusion->imu, holoscan::ConnectionOptions{.queue_depth = 32U});
add_flow(fusion->control, control.input(), holoscan::ConnectionOptions{.queue_depth = 8U});
```

Like the rest of the authoring surface, `import_topic` and `export_topic`
**throw** `RuntimeError` when a declaration is invalid — a malformed URI, a bad
option combination, or a payload type the boundary cannot carry. Authoring
throws; `compile()` returns rejected plans; run fails closed.

<Warning>
  **The URI is an identity, not a location.** The `holomq://` URI is an exact,
  case-sensitive topic identity — the scheme selects the interprocess
  transport, and the string must match exactly on both sides. It is
  descriptive: declaring it does not grant any process runtime attachment
  authority, and there is no host/port to tweak inside it.
</Warning>

## Naming the endpoint with `TopicOptions`

`TopicOptions` is the complete cold contract for one boundary. Its most
important field is `endpoint_name` — the explicit, deployment-stable name under
which the boundary appears in the endpoint catalog. External clients look
endpoints up **by this name**, so choose it the way you would choose a public
API name: stable across builds, meaningful to the peer team, never derived
from internal wiring details.

```cpp
holoscan::TopicOptions options;
options.endpoint_name = "frames";                 // the name external peers look up
const auto frames = g.import_topic<std::uint32_t>("holomq://frames", std::move(options));
```

Beyond the name, `TopicOptions` carries the rest of the boundary contract, all
declared cold at compose time:

- `capture_time` — a `RequireCaptureTime{clock}` requirement that inbound
  samples carry capture timestamps in a declared clock domain (see
  [Time and clocks](/holoscan/sdk-user-guide/getting-started/time-and-clocks)).
- `attach` — a `TopicAttachPolicy` selecting whether an absent external peer is
  acceptable. The default is optional: composition and graph start never wait
  for an external process.
- `bounds` — finite publisher/subscriber-side bounds (queue depths, claim
  counts), keeping the boundary bounded by construction like everything else
  in the runtime.
- Tensor- and schema-specific fields (`tensor`, `schema`,
  `memory_conversion`) that constrain what a Tensor or schema payload may look
  like at the boundary — see
  [Payload type rules](/holoscan/sdk-user-guide/data-and-payloads/payload-type-rules).

There is deliberately no backend option bag, raw handle, or device ordinal in
`TopicOptions`: the boundary contract stays backend-neutral and cold.

## The graph side binds automatically

Inside the graph, an external topic is *just another port*. Your operators
receive imported samples through their ordinary `Input<T>` ports and emit
through ordinary `Output<T>` ports; their `contract()` and `compute()` neither
know nor care that a sample crossed a process boundary. When you compile the
graph and start it, the runtime materializes the boundary transport for you:

```cpp
holoscan::ExecutionPlan plan = holoscan::compile(g);
if (!plan.ok()) { /* inspect the rejected plan */ }

holoscan::RunSession session = holoscan::run_async(plan);
// The imports and exports are now bound — no channel code was written.
```

You never construct a publisher, subscriber, or channel object on the graph
side. Declaring the topic *is* the entire graph-side involvement; binding is
the runtime's job at run.

<Warning>
  **One graph, one vocabulary.** Inside a graph, operators communicate through
  typed ports (`Input<T>`/`Output<T>`) wired with `add_flow()` — the runtime
  materializes the channels for you. The `ChannelRuntime` client API exists
  only for standalone processes outside any graph. Never mix the two: using
  `ChannelRuntime` inside an operator bypasses the compiled plan and its
  guarantees.
</Warning>

## The endpoint catalog: the boundary contract

When `compile()` accepts a graph, the resulting plan carries an **endpoint
catalog** describing every declared boundary — payload identity, endpoint
names, capacities, and queue policy. You reach it with
`plan.endpoint_catalog()`:

```cpp
const holoscan::ChannelEndpointCatalog& catalog = plan.endpoint_catalog();

// Hand the contract to a peer process as canonical JSON:
if (auto saved = catalog.save_json("/tmp/frames-catalog.json"); !saved) {
  // typed filesystem error — branch on saved.error().code
}
```

The catalog is the **only** thing a graph shares with an external process. The
peer loads the same JSON (`ChannelEndpointCatalog::load_json()`) and looks up
endpoints by the `endpoint_name` you declared; it inherits no compiled plan,
no in-memory objects, and no transport handles. This makes "what crosses the
boundary" a single inspectable artifact: if you can read the catalog JSON, you
can see the complete external surface of the application. Because the catalog
serialization is canonical, the same boundary always produces the same bytes,
and either process may start first.

Two practical consequences follow:

- **A differently built peer can attach.** The peer binary does not need to
  link against your application or share its build — only the catalog.
- **A stale catalog fails at attach, not at compile.** If you change a
  boundary (type, name, bounds), regenerate and re-share the catalog; a peer
  holding the old JSON is rejected when it tries to attach.

## What stays inside, what the outside sees

The boundary is asymmetric by design. Everything about *how* your pipeline
works stays private to the graph; only the declared endpoints are visible
outside.

| Stays inside the graph | Visible to external processes |
| --- | --- |
| Operators, their names, and their wiring | Endpoint names from `TopicOptions::endpoint_name` |
| Temporal contracts, triggers, missing-data policy | Payload identity (the exact `T` of each boundary) |
| Regions, clocks, lifecycle ordering | Queue policy, capacities, and declared bounds |
| The compiled plan and its internal channels | The `holomq://` topic identity |
| Everything else in `GraphView` | Nothing else — the catalog is exhaustive |

An external process cannot observe or influence your internal topology. It
sees a named, typed endpoint with declared bounds — nothing more. Conversely,
your operators cannot tell an external peer from an internal one: an imported
topic delivers samples through the same typed port machinery, subject to the
same temporal contracts, as any internal flow.

This is why the boundary belongs in *composing applications* rather than in a
networking chapter: you are not opening a socket, you are extending the typed
dataflow contract of the graph to one carefully named edge.

## Recap

- `import_topic<T>("holomq://…")` and `export_topic<T>("holomq://…")` declare
  typed external boundaries during composition; invalid declarations throw,
  like all authoring.
- `TopicOptions::endpoint_name` gives each boundary its deployment-stable
  public name; the rest of `TopicOptions` declares the cold boundary contract.
- Inside the graph, a boundary is just a port: wire `imported.output()` /
  `exported.input()` with `add_flow()`, and the runtime binds it automatically
  at run.
- `plan.endpoint_catalog()` is the entire external contract — serialize it
  with `save_json()` and share nothing else with peer processes.
- Internal topology, contracts, and wiring stay private; external processes
  see only named, typed, bounded endpoints.
