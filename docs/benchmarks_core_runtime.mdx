The SDK ships its runtime performance coverage in-tree under the top-level
`benchmark/` directory, alongside its correctness tests. This page separates
public transport-through-Graph measurements from implementation
microbenchmarks used by SDK developers. Channel-focused transport results are
covered on [Channel Benchmarks](/holoscan/sdk-user-guide/performance/channel-benchmarks).
Application sensor-to-actuation measurements are not yet available and remain
unpublished.

<Note title="You will learn">
- What one controlled x86_64 run measured through a running Graph.
- Which internal suites help SDK developers diagnose runtime costs locally.
</Note>

<Note title="Controlled x86_64 results">
  The tables report medians across seven repetitions on one controlled x86_64
  workstation. Single-process latency rows use at least 10,000 measured
  samples and report p50, p99, and p99.9. Interprocess latency rows use 1,000
  warmup plus 1,000 measured samples and deliberately stop at p99. Throughput
  is unpaced. The 1:1 and chain latency rows use 200 µs pacing and queue depth
  1; fanout latency uses queue depth 2. Throughput also uses queue depth 2.
</Note>

## Transport through a running Graph

The controlled suite reports comparable payload and process-topology
dimensions where matched HoloMQ, Channel, and Graph rows exist. Coverage is
not identical across all three layers. These are independent measurement
boundaries rather than additive substages: do not subtract one row from
another to infer framework overhead.

The table's latency boundary is `publication_to_receive`: its source timestamp
is taken immediately before `emit()`, after any producer-side Tensor loan
acquisition and writes, and its sink timestamp is taken immediately after
`receive()`. The docs preset uses descriptor-only raw Tensor and multi-Tensor
rows. Their compiler-owned pool backing is initialized during warmup, so no
backing `memset` occurs during measured publications; the rows isolate
descriptor publication, Runtime execution, retention, and receive. The full
callback and Tensor phase timings remain available in the artifacts, and the
runner retains a `full_write` profile for separate producer-work diagnostics.

`runtime_benchmark::MultiTensorMessageT` contains one `uint64` sequence plus
two independent rank-1 `uint8` pageable-host Tensor fields, `first` and
`second`. Each field is 1 MiB and has its own compiler-owned pool, for a 2 MiB
application payload. The interprocess 1:2 row uses queue depth 2 and 5 ms
pacing to provide the flow-control headroom required by that topology.

The p99 and p99.9 values are descriptive. Seven repetitions characterize this
controlled run but do not establish a tail-latency acceptance bound. In
particular, 1,000 measured interprocess samples support p99 but not a useful
p99.9 estimate, so the interprocess table omits that column.

The separate-partition fanout rows also expose rare scheduler stalls that are
not visible at p50 or p99: their median p99.9 values across repetitions were
1.703 ms for 1:2 and 2.305 ms for 1:4, and the per-repetition p99.9 values
varied substantially. The suite's publication gate applies to the primary p50
metric, so these tail values remain descriptive evidence rather than a passed
tail-latency bound.

The tables preserve logical publications/s and aggregate deliveries/s as
separate metrics. For fanout, one logical publication produces one delivery
per subscriber, so aggregate delivery rate scales with subscriber count. The
small 1:1 difference between the rates is measurement-window alignment, not
data loss. The paired single-process fanout rows compare one shared operator
partition with separate source and subscriber partitions. The shared rows
measure serial in-process HoloMQ fanout without cross-partition scheduling;
the separate rows assign every subscriber to its own pinned CPU and include
partition-owner wake and scheduling costs while allowing subscriber callbacks
to run in parallel. The Notes column records the wake mechanism present in the
measured build. This collection reports an event wake and
channel-pump thread for both configurations; they are not eventless
measurements.

For representative 1:1 rows, the running Graph measured 5.436–8.619 µs
single-process and 16.437–26.745 µs interprocess p50 latency. This boundary
includes Runtime wake-up, controller and any channel-pump coordination,
readiness selection, operator activation, and receive materialization. It is
therefore expected to cost more than the lower-level HoloMQ and Channel
measurements, but the boundaries are independently timed and must not be
subtracted to infer one internal stage.

### Reproducing the tables

From the repository root, first save the current CPU configuration and apply
the benchmark controls:

```bash
sudo ./public/benchmark/configure_cpu_performance.sh \
  apply /tmp/holoscan-cpu-performance.state
```

Then run exactly the rows used by this page in the SDK development container:

```bash
HOLOSCAN_CUDA_MAJOR_VERSION=13 ./public/run launch build-cu13-x86_64 \
  --security-opt=seccomp=unconfined \
  --run-cmd "setarch x86_64 -R \
    python3 ../benchmark/run_transport_benchmark_suite.py \
    --build-dir . \
    --output-dir transport-suite-docs-core-runtime-$(date +%Y%m%d-%H%M%S) \
    --preset docs-core-runtime \
    --cpus 0,1,2,3,4,5,6,7"
```

Generate the tables from the preserved artifacts, optionally updating this
page in place:

```bash
python3 public/benchmark/summarize_runtime_benchmarks.py \
  public/build-cu13-x86_64/transport-suite-docs-core-runtime-<timestamp> \
  --update-doc public/docs/benchmarks_core_runtime.mdx
```

Finally, restore the saved host CPU configuration:

```bash
sudo ./public/benchmark/configure_cpu_performance.sh \
  restore /tmp/holoscan-cpu-performance.state
```

See [Runtime benchmark hardware tuning](https://github.com/nvidia-holoscan/holoscan-sdk/blob/main/benchmark/runtime/HARDWARE_TUNING.md)
for GPU clock controls, Jetson controls, verification, and recovery commands.

## Running the suites locally

All commands run from the repository root that contains the `benchmark/`
directory. The `./run bench` helper executes inside the Holoscan build
container with a Release build by default, rebuilds any stale benchmark
targets, and runs the binaries directly so Google Benchmark output keeps its
normal formatting:

```bash
./run bench --help    # full command reference and commented examples
./run bench --list    # list registered benchmarks (CTest name + short alias)
./run bench           # build what is missing and run all benchmarks
```

You can target one suite by alias or CTest name — for example
`./run bench --name core_hello` and
`./run bench --name BENCHMARK_CORE_HELLO` are equivalent. Suites are also
registered with CTest under the `benchmark` label, so `ctest -L benchmark`
runs them from an existing build tree.

<Tip>
  Benchmark defaults keep runtimes short enough for frequent developer and CI
  smoke runs. For stable local measurements, use the reversible host tuning
  helper and explicit CPU placement described above, close background
  workloads, and use a production-quality preset.
</Tip>

## Recap

- Controlled representative 1:1 Graph p50 latency ranged from 5.436–8.619 µs
  in one process and 16.437–26.745 µs between two processes.
- Single-process rows report p99.9 from at least 10,000 measurements;
  interprocess rows use 1,000 measurements and stop at p99.
- The generated tables compare shared and separate-partition 1:2 and 1:4
  fanout, include a 10-operator single-process chain, and cover a generated
  schema with two preallocated Tensor fields.
- HoloMQ, Channel, and Graph measurements are independent boundaries; compare
  matched rows and do not subtract them.
- The internal microbenchmark inventory remains available for local diagnosis
  and CI smoke coverage; it is not the public transport result table.
