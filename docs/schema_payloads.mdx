If you need to move structured data between operators and do not want to declare
anything — no identity traits, no layout description, no serialization code — the SDK
schema types are the path of least resistance. They are FlatBuffers-backed message types
that ship with the SDK, ready to use as port types: declare
`Output<holoscan::schema::TimeT>` on one operator and `Input<holoscan::schema::TimeT>` on
another, wire them with `add_flow()`, and the runtime does the rest. The codec is chosen
automatically at `compile()` time, and exactly the same code works whether the connection
stays in-process or crosses a process boundary over an interprocess topic.

Each type carries its own pinned identity, verifier, and serialized-size bound. Use an
application-owned FlatBuffers schema when the SDK's message shapes do not fit; the same
generated owning-type experience extends to your `.fbs` definition. The
[experimental raw-POD path](/holoscan/sdk-user-guide/advanced/experimental-pod-payloads)
is reserved for expert applications that deliberately cannot use a schema compiler or
generated code.

**Complete C++ example:** [`examples/schema_payloads/cpp`](https://github.com/nvidia-holoscan/holoscan-sdk/tree/main/examples/schema_payloads/cpp)

  `ChannelRuntime` inside an operator bypasses the compiled plan and its
  guarantees.
</Warning>

## The SDK schema types

Four schema types are available directly as port payloads. Each is an owning native
value type — plain fields you read and write, no builder objects on the pipeline path:

| Type | Carries | Fields |
|---|---|---|
| `holoscan::schema::TimeT` | A timestamp pair | `time_ns`, `acqtime_ns` (both `int64_t`) |
| `holoscan::schema::StringT` | A variable-length string | `data` (`std::string`) |
| `holoscan::schema::ImageT` | One image frame and its pixels | `header`, `height`, `width`, `encoding`, `data` (a Core `Tensor`), `color_space`, `significant_bits`, `roi_offset_x`, `roi_offset_y`, `plane_layouts`, `exposure_time_ns`, `gain` |
| `holoscan::schema::ImuT` | One IMU sample | `header`, `orientation` (quaternion), `angular_velocity`, `linear_acceleration` (3-vectors), `flags`, `orientation_covariance`, `angular_velocity_covariance`, `linear_acceleration_covariance` (row-major 3x3 matrices) |

`ImageT` and `ImuT` are the two sensor payloads, and the two that share a `header`. What
that header promises, how to extend either payload, and what a schema change costs a
running deployment are covered in
[Sensor payloads](/holoscan/sdk-user-guide/data-and-payloads/sensor-payloads).
`ImuT` is the natural carrier for the high-rate leg of a fusion pipeline and `ImageT`
for the frame leg; the schema-payloads example above emits `ImuT` for exactly that.
`ImageT` keeps its pixels in a Core `Tensor` rather than inside the FlatBuffer, so frame
metadata and pixel storage stay bounded independently of each other; that makes it a
descriptor-Tensor payload, and an operator producing one declares its Tensor layout and
allocation bounds like any other Tensor-carrying port. `StringT` suits status,
description, and control-text messages. `TimeT` carries a capture/acquisition timestamp
pair when the payload itself *is* the timestamp.

Pick a schema type for ordinary structured messages: you skip manual identity and byte-layout
traits and gain verified variable-length, optional, and nested fields. Define an
application-owned schema when the SDK shape does not fit. Bulk device-backed data can use
a descriptor-Tensor schema; a direct [`Tensor`](/holoscan/sdk-user-guide/data-and-payloads/tensors-in-depth)
remains appropriate when the payload is only the Tensor.

## Zero declarations: emit and receive

There is no registration step, no attach call, and no trait to specialize. Use the type
as the port payload and the ordinary port verbs:

```cpp
class StatusSource final : public holoscan::Operator<> {
 public:
  void setup(holoscan::OperatorSpec& spec) override {
    spec.output(out, "status");
  }

  [[nodiscard]] holoscan::expected<void, holoscan::Error> compute(
      holoscan::ExecutionContext&) override {
    holoscan::schema::StringT status;
    status.data = "pipeline healthy";
    return out.emit(std::move(status));
  }

  holoscan::Output<holoscan::schema::StringT> out;
};
```

On the consumer side, `receive()` hands you an owning `Sample<T>` whose `data` member is
the native value, fields already populated and verified:

```cpp
class StatusSink final : public holoscan::Operator<> {
 public:
  void setup(holoscan::OperatorSpec& spec) override {
    spec.input(in, "status").queue_depth(1U);
  }

  [[nodiscard]] holoscan::expected<void, holoscan::Error> compute(
      holoscan::ExecutionContext&) override {
    auto sample = in.receive();  // expected<Sample<schema::StringT>, Error>
    if (!sample) { return holoscan::make_unexpected(std::move(sample).error()); }
    consume(sample->data.data);  // the StringT's string field
    return {};
  }

  holoscan::Input<holoscan::schema::StringT> in;
};
```

Emitting a `TimeT` is the same one-liner:

```cpp
return out.emit(holoscan::schema::TimeT{.time_ns = t, .acqtime_ns = a});
```

Wiring, compiling, and running are completely unchanged from any other payload type:
`add_flow()` connects the ports, `compile()` selects the schema codec for you, and the
plan either runs or is rejected with a reason. There is no codec opt-in and nothing
schema-specific in your graph code. If any of this is unfamiliar, start with
[Composing a graph](/holoscan/sdk-user-guide/getting-started/composing-a-graph) and
[Payload type rules](/holoscan/sdk-user-guide/data-and-payloads/payload-type-rules).

## In-process and cross-process, same code

A schema value is carried as a self-contained encoded envelope. Inside one process this
detail is invisible — you emit a native value and receive a native value. The payoff
comes at a process boundary: because the envelope is self-describing and
portable-by-construction, the *same* operator code works when the connection is exported
over an interprocess topic. No `#ifdef`, no alternate serialization path, no
transport-aware code in `compute()`.

On every receive, the runtime verifies the encoded bytes first (a FlatBuffers verifier
pass) and only then materializes the owning native value. A malformed or truncated frame
from an external process is rejected with a typed error and never reaches your
`compute()`. See
[Interprocess channels](/holoscan/sdk-user-guide/advanced/interprocess-channels) for
exporting a connection, and
[Standalone channel clients](/holoscan/sdk-user-guide/advanced/standalone-channel-clients)
for feeding a graph from a non-operator process.

<Warning>
  **Schema payloads are bounded — size for the cap.** Every schema type has a
  compile-time maximum serialized size,
  `generated_schema_max_serialized_size_v<T>`. A value that encodes larger than
  the cap — for example, a very long `schema::StringT` — fails with a typed
  `kResourceExhausted` error instead of allocating without bound. This is the
  same bounded-by-construction rule as everywhere else in the runtime: treat the
  cap as part of your message design, not as an error to discover in the field.
</Warning>

## Schema identity pinning

Every schema type carries a pinned identity with four components, all supplied by the SDK
type itself:

- a **canonical name** — globally scoped and dotted, e.g. `holoscan.schema.Time`;
- a **version** — a monotonically bumped integer;
- a **content hash** — the SHA-256 digest of the compiled schema artifact, so the
  identity covers the schema's actual field layout, not just its name;
- a **stable 128-bit schema id** — a compact fingerprint derived from the above.

*Pinned* means matched **exactly**: a producer and a consumer agree on a schema payload
only if all four components are equal. There is no negotiation protocol, no
field-evolution policy, and no "close enough". At a process boundary the agreement is
checked twice. Attaching an endpoint compares the complete four-component tuple and
refuses a mismatch with a typed `kIncompatible` error, so a wrong peer never reaches
steady state. Every received frame then revalidates the identity its envelope carries
and fails with a typed `kProtocolError` before a single payload byte is exposed.

Inside one process the C++ type system already enforces most of this: `add_flow()` only
connects an `Output<T>` to an `Input<T>` of the same `T`. Identity pinning earns its keep
at process boundaries, where the type system cannot reach. Because the content hash is in
the identity, two builds that disagree about what `holoscan.schema.Imu` looks like —
say, one side was compiled against an older SDK whose IMU schema had different fields —
cannot silently exchange misinterpreted bytes: the hash differs, the frame is refused,
and you get a diagnosable error instead of corrupted sensor data.

For SDK schema types this is entirely automatic — the identity ships inside the SDK, so
both sides of a connection built against the same SDK release agree by construction. You
never write, register, or compare an identity yourself.

## Generate an application-owned schema

When the SDK shapes do not fit, define the message in an application-owned `.fbs` file and use the
installed `holoscan_add_flatbuffer_schema()` CMake function. It runs the matching schema compiler
and generates the FlatBuffers headers, owning object-API type, exact schema identity, bounded codec,
package evidence, native traits, and Runtime type operations.

Application Operators use the generated owning type directly:

```cpp
holoscan::Output<app::CustomControlT> output;
holoscan::Input<app::CustomControlT> input;
```

Values then use the same `emit()`, `receive()`, graph composition, and cross-process path as the SDK
schema types. Application code does not specialize schema traits, hand-pin a digest, or expose an
inline transport wrapper as its port type. The complete generation call, `.fbs` example, supported
field shapes, and descriptor-Tensor variant are documented in
[Custom FlatBuffer schemas](/holoscan/sdk-user-guide/data-and-payloads/custom-flatbuffer-schemas).

## Experimental exception: raw POD

The [experimental raw-POD path](/holoscan/sdk-user-guide/advanced/experimental-pod-payloads) is a
separate expert escape hatch for fixed-layout messages that deliberately cannot depend on a schema
compiler or generated code. It requires an explicit identity and an exact byte-covering field
layout; the application owns binary compatibility, schema evolution, and coordinated deployment.
Do not use raw POD as the ordinary alternative to an SDK schema type.

## Recap

- SDK schema types (`schema::TimeT`, `schema::StringT`, `schema::ImageT`,
  `schema::ImuT`) are the zero-declaration payload path: use them directly as
  `Output<T>`/`Input<T>` types. The sensor payloads among them, `schema::ImageT` and
  `schema::ImuT`, are owned by `holoscan::sensor_io` rather than by Core, so carrying
  either one means linking that library and installing the `holoscan-sensor-io`
  component. The type names are unchanged: a FlatBuffers namespace is part of the wire
  identity, so these stayed `holoscan::schema::*` when their ownership moved.
- The codec is selected automatically at `compile()`; the same operator code works
  in-process and across processes.
- Received values are verified before delivery and arrive as owning native values with
  fields populated.
- Serialized size is bounded by `generated_schema_max_serialized_size_v<T>`; overflow is
  a typed `kResourceExhausted`, never unbounded allocation.
- Identity is pinned — canonical name + version + content hash (+ stable 128-bit id) —
  and matched exactly; a peer whose tuple differs is refused at attach with
  `kIncompatible`, and a frame whose envelope identity differs fails with
  `kProtocolError` before delivery.
- Application-owned `.fbs` files generate owning port types and package traits — see
  [Custom FlatBuffer schemas](/holoscan/sdk-user-guide/data-and-payloads/custom-flatbuffer-schemas).
