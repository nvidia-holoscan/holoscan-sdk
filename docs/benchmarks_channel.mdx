Holoscan channels are built on HoloMQ, a typed shared-memory transport. This
page explains how to read their hot-path measurements for the two payload
families you will use most: small POD values carried inline through the
transport, and Tensors carried as descriptors while the payload bytes stay in
place. Read
[the performance model](/holoscan/sdk-user-guide/performance/performance-model)
first if you have not — the vocabulary here (serialized vs. saturated,
delivery cycle vs. one-way E2E) comes from that page.

The controlled result set below comes from one Release build and one tuned
x86_64 workstation. The older measurements later on this page remain useful
evidence of cost *structure*, but the controlled tables are the current
reference for this machine. They are measurements, not guarantees for your
hardware.

<Note title="You will learn">
- What one controlled x86_64 run measured for HoloMQ and Channel latency and
  throughput.
- How the two Tensor transports differ: same-process sidecar vs. interprocess
  `BufferHandle` descriptor import.
- Why serialized and saturated results must never be compared directly.
- How publish cost grows with fanout (1:1, 1:2, 1:4) for both Tensor paths.
- Which provenance must accompany every published result.
</Note>

<Warning>
  **One graph, one vocabulary.** Inside a graph, operators communicate through
  typed ports (`Input<T>`/`Output<T>`) wired with `add_flow()` — the runtime
  materializes the channels for you. The `ChannelRuntime` client API exists
  only for standalone processes outside any graph. Never mix the two: using
  `ChannelRuntime` inside an operator bypasses the compiled plan and its
  guarantees.
</Warning>

### CUDA stream-ordering control

The device-buffer control separates raw descriptor transport from
stream-ordered ownership. All four rows reuse backing initialized before
timing; they differ only in the CUDA readiness and release protocol applied
to each publication.

| Producer readiness | Consumer deferred release | Logical messages/s | Paced p50 | Paced p99 |
| --- | --- | ---: | ---: | ---: |
| No | No | 767,705 | 1.072 µs | 1.367 µs |
| Yes | No | 43,957 | Not measured | Not measured |
| No | Yes | 363,661 | Not measured | Not measured |
| Yes | Yes | 12,372 | 3.197 µs | 4.507 µs |

The fully stream-ordered row is the relevant lower-level control when a
producer changes device contents on one stream and a consumer uses them on
another. It enqueues a generation write, a generation wait, and deferred
producer and consumer refcount releases. Its 74.281 µs
pool-acquisition p50 shows that stream-ordered slot recycling, not the
BufferHandle descriptor itself, limits this implementation under saturation.
By contrast, the descriptor-only row needs no fence because initialization
completed before publication.

## How to read these tables

Two execution models appear throughout, and they measure different things:

- **Serialized**: one thread calls `emit_sample()` and then immediately calls
  `receive_sample()` on the paired endpoint, with exactly one sample in
  flight. The **delivery cycle** is the emit-plus-receive round through the
  transport. This isolates API cost cleanly.
- **Saturated**: publisher and subscriber run concurrently on separate
  threads or processes with no pacing and a queue depth of 64. The **one-way
  E2E p50** runs from the publisher's timestamp to completed receive and
  includes queue residence and scheduling. Because several samples are in
  flight, completed samples per second can *exceed* `1 / E2E` — throughput is
  a pipelined completion cadence, not the reciprocal of latency.

Every `emit`/`receive` in these benchmarks carries a full `Sample<T>` — the
value plus its `SampleMetadata` — even when the convenience `emit(T)` /
`receive()` overloads are used.

## POD inline transport

POD payloads travel inline: the bytes of `T` and the `SampleMetadata` are
copied into the transport sample itself. The same code path serves
same-process and interprocess deployments — only the queue's process
placement changes.

| POD execution model | Measured interval | Median | Completed samples/s |
| --- | --- | ---: | ---: |
| Same process, same thread | Serialized emit + receive delivery cycle | 583 ns | 1.716 M/s |
| Same process, publisher and subscriber threads | One-way E2E p50 | 1,333 ns | 1.118 M/s |
| Separate publisher and subscriber processes | One-way E2E p50 | 1,304 ns | 1.128 M/s |

Breaking the saturated rows into per-call API cost:

| Deployment | `emit_sample()` p50 | Successful `receive_sample()` p50 | E2E p50 |
| --- | ---: | ---: | ---: |
| Same process, inline | 789 ns | 500 ns | 1,333 ns |
| Separate processes, inline | 778 ns | 467 ns | 1,304 ns |

The near-identical intraprocess and interprocess rows are expected, not a
fluke: both use the same typed inline transport path, so crossing a process
boundary costs essentially nothing extra for POD payloads on this host.

<Warning>
  Do not add the emit and receive medians to reconstruct latency. The two
  calls execute on different threads or processes and overlap with transport
  and scheduling; their sum is not the end-to-end path. Likewise, the 583 ns
  same-thread delivery cycle has no publisher-to-subscriber timestamp and
  must not be read as concurrent latency.
</Warning>

## Tensor transport: sidecar vs. BufferHandle

Tensor payloads never copy their bytes through the queue. Two mechanisms
carry them:

- **Same-process sidecar**: the publisher stores the Tensor handle in a
  runtime-owned sidecar store and publishes a small descriptor. The
  subscriber resolves the descriptor and receives *the same underlying Tensor
  allocation* — no import, no new view.
- **Interprocess `BufferHandle`**: the publisher exports a descriptor
  encoding a `BufferHandle` plus shape, strides, and dtype. The subscriber
  imports the referenced pool slot (cached after first import) and
  materializes a new read-only Tensor view whose lifetime is tied to the
  lease.

### Serialized comparison (one sample in flight)

Both rows use the same warmed pinned-host source pool, so the difference is
purely the transport choice:

| Tensor path | Emit stage | Receive stage | Delivery cycle | Delivery cycles/s |
| --- | ---: | ---: | ---: | ---: |
| Same-process sidecar, pinned-host-backed Tensor | 591 ns | 357 ns | 890 ns | 1.124 M/s |
| `BufferHandle`, same pinned-host source pool | 701 ns | 637 ns | 1,300 ns | 0.769 M/s |

These are Google Benchmark median aggregates of repetition-level mean
iteration times, not per-operation percentiles. The stage columns and the
delivery-cycle column come from separate benchmark rows and are not
mathematically additive; the delivery-cycle value is authoritative.

### Saturated comparison (production runner, 1 MiB device Tensor)

| Payload and deployment | `emit_sample()` p50 | Successful `receive_sample()` p50 | E2E p50 | Completed/s |
| --- | ---: | ---: | ---: | ---: |
| Tensor, same process, sidecar | 1,174 ns | 730 ns | 2,028 ns | 758,847 |
| Tensor, separate processes, device `BufferHandle` | 1,046 ns | 1,004 ns | 2,369 ns | 846,421 |

<Warning>
  **The serialized and saturated tables are not directly comparable.** They
  measure different execution models: the serialized rows time one sample in
  flight with no concurrency, while the saturated rows include queue
  residence, scheduling, and cross-thread or cross-process handoff under full
  load. Compare cost *structure* across them (sidecar receive stays cheaper;
  `BufferHandle` receive pays for import and view materialization), never
  their absolute medians. Note also that the serialized rows above use
  pinned-host-backed Tensors while the saturated rows use device Tensors.
</Warning>

Structurally, sidecar receive reuses the existing Tensor handle, whereas
`BufferHandle` receive imports a pool slot and materializes a new Tensor
view — that is why the interprocess receive p50 is markedly higher even
though its emit is competitive. The interprocess row can still complete more
samples per second because publisher and subscriber pipeline across process
boundaries.

Putting the saturated 1:1 rows from both payload families side by side makes
the cost structure visible at a glance: both POD deployments land at ~1.3 µs,
and the two Tensor descriptor paths sit roughly 0.7–1.1 µs above them.

The takeaway: the sidecar store is *not* the dominant cost. Raw typed
transport occupies roughly 80% of the serialized path, and within that, the
publisher stage (loan, payload assignment, send — about 421 ns at batch depth
one) is the largest measured substage; subscriber take-and-copy is about
232 ns. The release callback exists because sidecar and `BufferHandle`
publications carry external ownership; self-contained POD payloads omit it
entirely. These deltas come from matched whole-path benchmark pairs, so they
can be displayed additively; the independently timed substages cannot be
subtracted from other rows as if they shared one clock.

## Earlier-reference provenance and caveats

All results were collected on a single workstation: an Intel Core i9-10980XE
(18 physical cores, SMT enabled) running Linux, from a Release build
(`CMAKE_BUILD_TYPE=Release`, clang-tidy off) with CUDA 13, inside the
matching SDK container. ASLR and normal frequency scaling remained enabled.

- **Concurrent POD rows**: 2026-07-10 production matrix at commit
  `2369aea9c`. One million measured samples after 10,000 warmup samples,
  queue depth 64, no publisher pacing, publisher pinned to a dedicated core,
  subscribers on distinct physical cores.
- **Same-thread POD row**: focused 11-repetition Release run on 2026-07-12
  (583 ns median), after configuring exact subscriber capacity and omitting
  the unused release handler. A directly comparable raw-HoloMQ POD benchmark
  measured 632 ns in the same session; that cross-binary ordering is
  sensitive to code layout and run order and should not be read as negative
  channel overhead.
- **Tensor rows (serialized, saturated, fanout)**: refreshed on 2026-07-12 at
  commit `1d06c716a`, with exact subscriber capacity configured and
  local-only CUDA FD export disabled. Fanout rows used 100,000 measured
  samples after 10,000 warmup samples, queue depth 64, final payload
  validation; all rows completed without sequence gaps.

Interpretation constraints — read these before quoting any number:

- **Device rows measure descriptor transport only.** They transport
  descriptors, import pool slots, and materialize Tensor views; they do not
  copy 1 MiB of payload data or execute any real GPU work. CUDA
  generation-ordering waits and stream-ordered deallocation can dominate a
  real stream-ordered interprocess pipeline and are deliberately excluded
  here.
- **Percentiles are post-warmup and successful-calls-only.** Production-run
  p50 values are nearest-rank percentiles over individual successful samples
  after warmup; subscriber `kNotReady` polls are not included in the
  successful-receive durations.
- **Saturated E2E is not idle-system latency.** The concurrent runs are
  saturated throughput tests; E2E percentiles include queue residence and
  scheduling.
- **Small deltas need isolated reruns.** With ASLR and frequency scaling
  enabled, confirm small cross-run differences with repeated isolated runs
  before using them to gate an optimization.

## Recap

- Intraprocess Channel measured 1.124 million `BenchmarkPod64` messages/s
  with 1.496 µs p50 latency; the closest concurrent HoloMQ polling control
  measured 1.230 million messages/s and a 1.253 µs mean iteration.
- In the controlled interprocess 1:1 run, HoloMQ delivered 64-byte values at
  1.323 million messages/s with 0.718 µs p50 latency; Channel delivered
  `BenchmarkPod64` at 1.183 million messages/s with 1.451 µs p50 latency.
- A 1 MiB device `Tensor` reached 700,028 messages/s and 2.280 µs p50 through
  Channel; device `ImageT` reached 525,397 messages/s and 3.428 µs p50.
- Earlier July measurements remain historical evidence, not current release
  results or performance guarantees.
- Tensor bytes never cross the queue: same-process sidecar reuses the
  original Tensor allocation, interprocess `BufferHandle` imports and
  materializes a new view.
- Serialized and saturated benchmarks measure different execution models —
  compare structure, never absolute medians.
- Publisher cost grows with fanout and becomes the limiting stage in both
  Tensor transports.
- Raw typed transport is ~80% of the sidecar delivery cycle; sidecar
  bookkeeping (~103 ns) and the release callback (~55 ns) are not the
  bottleneck.
- Device rows exclude GPU work; treat them as transport cost, not pipeline
  latency.
